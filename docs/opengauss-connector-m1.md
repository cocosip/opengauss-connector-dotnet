# M1 Starter Checklist

2026-11-24 · Applies to the first port and offline acceptance

M1 starts from a fixed ADO.NET snapshot. Seven NuGet packages are produced from the same source tree, each providing five asset groups: `netstandard2.0`, `netstandard2.1`, `net8.0`, `net9.0`, and `net10.0`. The work proceeds per the table below; the against-a-live-server environment can be prepared in parallel. ## First build and test entry point

After completing the project and test configuration above at the repository root, use the following commands. Run each next step only after the previous one succeeds. When creating a new solution, use `dotnet new sln --name OpenGaussConnector --format slnx`. The repository does not set `global.json`; it uses the .NET 10 SDK already installed on the development machine (this run: `10.0.403`), and the actual version goes into the acceptance record. [SLNX, CPM, and Package Validation](references.md#net-and-nuget-official-material)

```powershell
dotnet --info
dotnet sln OpenGaussConnector.slnx list
dotnet restore OpenGaussConnector.slnx
dotnet build OpenGaussConnector.slnx -c Release --no-restore
dotnet test OpenGaussConnector.slnx -c Release --no-build --filter "TestCategory=Offline"
dotnet pack OpenGaussConnector.slnx -c Release --no-build --include-symbols '-p:SymbolPackageFormat=snupkg' -o artifacts/packages
```

Keep the upstream test frameworks, marking `Offline` or `Integration` with NUnit's `Category` attribute and xUnit's `Trait("TestCategory", ...)`. VSTest matches NUnit categories as `TestCategory`, while xUnit matches by the specified Trait key. The offline path covers connection strings, the factory, generator output, DI lifetimes, and mapping, tracing, or contract cases that can run offline. Check that every project expected to contain offline cases actually discovers and executes those cases, and that test discovery and fixture initialization do not attempt to connect to a database in offline mode either. The full build includes against-a-live-server cases; GIS, specification, trimming, or benchmark cases that clearly need a server are executed by the against-a-live-server entry point. [Microsoft test filtering rules](references.md#net-and-nuget-official-material)

The upstream `TestUtil.cs`, `OpenGaussDbFactoryFixture.cs`, trimming programs, and benchmark helper code use `NPGSQL_TEST_DB`, and some entry points fall back to a default connection string when the configuration is missing. After the port, the against-a-live-server entry point reads the test connection string explicitly and records the reason when the configuration is missing. When acceptance against a live server is explicitly requested, a missing required connection string is reported as a configuration error. Check the impact of `TestGeoJSONTests` and `NetTopologySuiteTest` on test discovery, and record compilation, discovery, actual execution, and environment-skipped counts separately. Trimming and Native AOT publish acceptance are covered in B07.

## Seven-package consumption and M1 completion criteria

- [ ] Check the seven `.nupkg` files: core, DependencyInjection, GeoJSON, Json.NET, NetTopologySuite, NodaTime, and OpenTelemetry. For each package, verify the five `lib/<TFM>/` groups, the `.nuspec` dependency groups, the README, the license, and the matching symbol artifacts. All six extension packages pin the core dependency lower bound to the same release version.
- [ ] Restore an independent consumption project from the local package source generated in this run. Use an isolated package cache and make sure the seven package IDs in the artifacts resolve to the packages generated in this run. Check the compile and runtime assets and the actually resolved versions in `project.assets.json`, and verify the DLLs loaded at runtime. For DI and the base dependencies selected per TFM, check the minimum version and the selected compatible patch version separately.
- [ ] Run the corresponding modern assets on .NET 8, 9, and 10 hosts. Compile a caller for each of the two Standard targets and explicitly run the corresponding Standard DLL in an independent consumption case. Windows .NET Framework 4.8 is a candidate host for `netstandard2.0`; record coverage per the measured results.
- [ ] Add batch API binding cases from Standard to the modern assets. Compile a Standard class library that calls `CreateBatch` and the public signatures involving the shim, then have a modern application that restores packages normally call that class library, confirming that NuGet selected the modern asset. Verify which assembly the identically named types such as `DbBatch` live in. If binding fails, adjust the cross-TFM API approach first, and record the affected signatures and their migration path before release.
- [ ] Record the offline results, asset selection, dependency versions, and porting-compatibility conclusions for the seven packages. Real-server functionality and the against-a-live-server smoke test of the five asset groups are recorded in M2/M3, with results filled in per the [development progress](opengauss-connector-progress.md#acceptance-log).

## M2 environment inputs

M1 can start without an openGauss server configured. M2 requires a reachable 6.0.6 LTS environment; first create a single-node test database. For the A, B, and PG modes that can actually create databases, record the version and build number, the distribution form, the compatibility mode after connecting, the authentication configuration, and the test account privileges. TLS, primary/standby, and PostGIS cases additionally record certificates, topology, database extension versions, and applicable modes. 7.0.0 LTS enters M3 with the same record format. The user's actual deployed version and upgrade history are pending collection, and acceptance results are filled in per the actual environment.
